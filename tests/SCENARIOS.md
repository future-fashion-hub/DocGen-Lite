# Тестовые сценарии проекта DocGen Lite

Документ можно использовать как готовый раздел отчета по практической работе.

## Контекст
- Проект: генератор HTML-документации для C/C++ кода.
- Цель сценарного тестирования: проверить работу ключевых этапов программы в приближенных к реальным условиях.
- Формат каждого сценария: цель, входные данные, шаги, ожидаемый результат, что проверяется.

## Сценарий 1. Проверка CLI-параметров
- Идентификатор: `SC-01`
- Реализация: `tests/scenarios/scenario_cli_run.cpp`
- Цель:
  - Проверить, что конфигурация корректно читает аргументы запуска.
  - Проверить обработку флагов `-i`, `-o`, `--exclude`, `--open`.
- Входные данные:
  - Параметры командной строки (симулируются в мини-программе).
- Шаги:
  1. Запустить `scenario_cli_run`.
  2. Программа формирует набор аргументов и передает их в `Config::loadFromArgs`.
  3. Проверяется, что путь выхода прочитан корректно.
- Ожидаемый результат:
  - В консоли выводится `SCENARIO OK: args parsed, output=...`.
- Что проверяется:
  - Корректность парсинга аргументов.
  - Базовая готовность конфигурации для дальнейшей генерации.

## Сценарий 2. Разбор кода с комментариями и тегами
- Идентификатор: `SC-02`
- Реализация: `tests/scenarios/scenario_parse_sample.cpp`
- Цель:
  - Проверить этапы парсинга на примере входного C++-фрагмента.
  - Подтвердить извлечение сущностей и doc-тегов `@...`.
- Входные данные:
  - Тестовый текст заголовочного файла:
    - класс,
    - поле,
    - метод,
    - комментарии с `@brief`, `@param`.
- Шаги:
  1. Запустить `scenario_parse_sample`.
  2. Мини-программа создает `SourceFile` с тестовым содержимым.
  3. `Parser` выполняет разбор.
  4. Подсчитываются найденные классы, методы и теги.
- Ожидаемый результат:
  - В консоли вывод вида `SCENARIO RESULT classes=... methods=... tagged=...`.
  - Значения должны быть ненулевыми для проверяемых сущностей.
- Что проверяется:
  - Работа парсера и стратегии разбора.
  - Связка “комментарий -> сущность”.
  - Извлечение структурированных тегов документации.

## Сценарий 3. Генерация HTML-документации из модели
- Идентификатор: `SC-03`
- Реализация: `tests/scenarios/scenario_generate_html.cpp`
- Цель:
  - Проверить, что генератор создает документацию из набора сущностей.
- Входные данные:
  - Программно сформированная модель `SourceFile` с классом и методом.
- Шаги:
  1. Запустить `scenario_generate_html`.
  2. Мини-программа формирует тестовые сущности.
  3. Вызывает `HTMLGenerator::generate`.
- Ожидаемый результат:
  - Появляется директория документации `build/scenario_html`.
  - В консоли выводится `SCENARIO OK`.
- Что проверяется:
  - Создание основных HTML-страниц.
  - Базовая интеграция генератора с моделью данных.

## Сценарий 4. Полный цикл на структуре реального проекта
- Идентификатор: `SC-04`
- Реализация:
  - запуск `docgen` напрямую или
  - запуск `generate-docs.bat`.
- Цель:
  - Проверить интеграционный pipeline целиком:
    - сканирование файлов,
    - парсинг,
    - генерация документации,
    - обновление итоговых страниц.
- Входные данные:
  - Входная директория проекта (`.` или `src/include`),
  - выходная директория `build/docs`.
- Шаги:
  1. Запустить генерацию.
  2. Проверить лог: количество обработанных файлов/классов/функций.
  3. Открыть `build/docs/index.html`.
  4. Убедиться в наличии навигации, страниц классов/файлов и блока тегов.
- Ожидаемый результат:
  - Документация пересоздана в одной выходной директории.
  - Лог отражает статистику.
  - HTML-страницы доступны для просмотра.
- Что проверяется:
  - Конечный пользовательский сценарий использования программы.

## Что покрыто unit-тестами и для чего

Ниже перечислены ключевые классы и назначение их тестирования.

- `Config`:
  - проверка парсинга аргументов, валидации путей, списков исключений и флага `--open`;
  - цель: исключить ошибки запуска из-за некорректной конфигурации.

- `FileUtils`:
  - проверка операций с путями/директориями, рекурсивного обхода и удаления;
  - цель: гарантировать надежную файловую инфраструктуру генератора.

- `FileScanner`:
  - проверка фильтрации расширений, чтения содержимого и исключения директорий;
  - цель: корректно формировать набор файлов для парсинга.

- `Comment`, `CodeEntity`, `Parameter`, `FieldEntity`, `MethodEntity`, `ClassEntity`:
  - проверка хранения данных, рендеринга, работы с тегами и сигнатурами;
  - цель: корректность внутренней модели документации.

- `StandardCppStrategy` и `Parser`:
  - проверка распознавания классов/методов/полей, обработки комментариев и тегов, граничных случаев;
  - цель: устойчивый синтаксический разбор исходников.

- `SourceFile`, `SourceFileBuilder`, `Observable/Observer`, `Logger`:
  - проверка служебной логики хранения, построения объектов, уведомлений и логирования;
  - цель: стабильность вспомогательной инфраструктуры.

- `HTMLGenerator`:
  - проверка генерации страниц, копирования стилей, очистки старых артефактов, отображения секции с тегами;
  - цель: гарантировать корректный и воспроизводимый итоговый HTML-результат.

## Как запускать в отчете
- Unit-тесты:
  - `ctest --test-dir build --output-on-failure`
- Сценарии:
  - `./build/tests/scenario_cli_run`
  - `./build/tests/scenario_parse_sample`
  - `./build/tests/scenario_generate_html`

## Критерий приемки
- Все unit-тесты проходят успешно.
- Все сценарные мини-программы завершаются без ошибок и дают ожидаемые сообщения.
- Документация формируется в целевой директории и открывается для проверки.
